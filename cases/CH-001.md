# CH-001 — Successful INSERT Retry Without an Increase in Row Count

> **Simulation based on a documented ClickHouse behavior.** The customer ticket below is fictional. The SQL execution and recorded outcomes are from a real personal ClickHouse Cloud lab, not from a customer's production service.

## 1. Customer report (simulated)

> "Our application retries INSERT requests when a connection is interrupted. The retries are reported as successful, but the number of stored security-event records does not increase. Are we losing events?"

**Intake assessment:** Product reported as ClickHouse Cloud; ingestion/retry concern. Affected production service, timestamps, insert request IDs, impact, expected versus observed counts, and error responses are **not known** from an actual customer. Severity is therefore **not assigned**.

**Customer questions before accessing production:**
1. Which service, database and table are affected, and what access is authorized?
2. What were the exact client-side responses, timestamps, request/query IDs, and retry behavior?
3. How many **unique** events should have been stored? Are repeated requests identical or intentionally new?
4. Is ingestion entirely blocked, or are only repeated requests in question? Is an active security investigation affected?
5. Can the customer provide redacted INSERT statements, settings and diagnostic output without sharing sensitive events?

For this lab, access was limited to my own simulated environment.

## 2. Environment discovery (observed)

The investigation began with read-only discovery, rather than assuming the schema because I had created the environment.

```sql
SHOW DATABASES;
SHOW TABLES FROM support_lab;
DESCRIBE TABLE support_lab.windows_security_events;
SHOW CREATE TABLE support_lab.windows_security_events;
```

**Observed:** Five database names were visible, including `support_lab`. Its initial events table was `windows_security_events`, with six synthetic rows. The discovered schema contained `event_time`, `hostname`, `event_id`, `username`, `source_ip` and `description`.

The console truncated part of the `SHOW CREATE TABLE` output, so I inspected the system metadata rather than guessing:

```sql
SELECT name, engine, sorting_key, partition_key
FROM system.tables
WHERE database = 'support_lab'
  AND name = 'windows_security_events';
```

**Observed:** Engine `SharedMergeTree`; sorting key `event_time, hostname, event_id`; empty partition key (no explicit partitioning).

Initial row-count baseline:

```sql
SELECT count() AS current_rows
FROM support_lab.windows_security_events;
```

**Observed:** `6` rows. This is **not** evidence that six is the correct number expected by a real customer.

## 3. Hypothesis and settings (observed)

A successful retry that does not produce additional rows could be explained by insert deduplication. Other possibilities include unsuccessful upstream delivery, asynchronous buffering, filters used when counting, or retry logic. None was assumed as the cause without a test.

The following read-only query inspected settings **for the current SQL session**, not guaranteed settings for any customer's application:

```sql
SELECT name, value, changed
FROM system.settings
WHERE name IN (
    'async_insert',
    'wait_for_async_insert',
    'insert_deduplicate',
    'async_insert_deduplicate'
)
ORDER BY name;
```

| Session setting | Observed value | `changed` |
| --- | --- | --- |
| `async_insert` | `1` | `1` |
| `wait_for_async_insert` | `1` | `1` |
| `insert_deduplicate` | `1` | `0` |
| `async_insert_deduplicate` | `1` | `1` |

The `changed` flag indicates whether a setting differs from its default **in this SQL session**. The `insert_deduplicate` setting had `changed = 0`, while the other three had `changed = 1`. These results do **not** prove what settings a separate customer application used.

## 4. Controlled reproduction (observed)

A **separate test table** was created, so the original six synthetic security events were not changed:

```sql
CREATE TABLE support_lab.insert_retry_test
(
    batch_id String,
    event_id UInt32,
    message String
)
ENGINE = MergeTree()
ORDER BY (batch_id, event_id);
```

The starting count was verified using:

```sql
SELECT count() AS initial_rows FROM support_lab.insert_retry_test;
```

**Observed baseline:** `0`.

**First insert (executed once):**

```sql
INSERT INTO support_lab.insert_retry_test
(batch_id, event_id, message)
VALUES
('CH001-BATCH01', 4625, 'Failed login attempt'),
('CH001-BATCH01', 4720, 'User account created');
```

**Observed:** INSERT succeeded. A subsequent `SELECT * FROM support_lab.insert_retry_test;` returned the two records.

**Identical retry:** The same INSERT statement and values were executed again, once, without intentionally changing settings.

**Observed:** The retry returned `INSERT succeeded`, while:

```sql
SELECT count() AS total_rows
FROM support_lab.insert_retry_test;
```

still returned **`2`**, not `4`.

**Diagnostic corroboration:**

```sql
SELECT
    event_time,
    event_type,
    error,
    errorCodeToName(error) AS error_name
FROM system.part_log
WHERE database = 'support_lab'
  AND table = 'insert_retry_test'
ORDER BY event_time DESC
LIMIT 10;
```

**Observed:** The first write produced a normal operation with error code `0`; the retry produced error code **`389` — `INSERT_WAS_DEDUPLICATED`**. This was the decisive evidence connecting the unchanged row count to deduplication **in the reproduction**.

**Distinct new insert:**

```sql
INSERT INTO support_lab.insert_retry_test
(batch_id, event_id, message)
VALUES
('CH001-BATCH02', 4625, 'New failed login event');
```

After querying the records, **three total rows** were present: two from `CH001-BATCH01` and one from `CH001-BATCH02`.

Note: `batch_id` here is an application-defined field for readability, **not** automatically ClickHouse's deduplication identifier.

## 5. Findings and technical interpretation

| Check | Observed result |
| --- | --- |
| Test table initially | 0 rows |
| First INSERT | 2 rows persisted |
| Identical successful retry | Still 2 rows |
| `system.part_log` | `INSERT_WAS_DEDUPLICATED` (389) |
| Different subsequent INSERT | 3 total rows |

**Conclusion for this lab:** The same batch was recognized as a duplicate and skipped on retry, while different new data was still accepted. This is consistent with intended insert deduplication semantics; it is **not evidence of data loss** in the experiment.

**Limitations:** This was a small, single-service simulation. It did not reproduce a network failure or test client retry SDKs, token reuse, deduplication-window expiry, multi-replica behavior, or a real customer's configuration. It cannot establish whether a customer's allegedly missing *unique* events were actually ingested.

## 6. Customer update (proposed wording; not sent)

> We reproduced the symptom in an isolated ClickHouse Cloud test. Repeating an identical successful INSERT did not increase the row count. The internal part log recorded `INSERT_WAS_DEDUPLICATED` (389), and a genuinely different INSERT was persisted normally. This indicates expected deduplication behavior in our test, not a confirmed production data-loss incident. To determine whether the same mechanism explains your reported events, please provide redacted examples of affected requests, their timestamps/query IDs, expected unique event counts, and relevant ingestion diagnostics. We recommend retaining retry deduplication while we review how the application constructs and retries batches.

## 7. Escalation decision and closure criteria

**No engineering escalation warranted solely by the controlled reproduction:** behavior was consistent with the documented mechanism.

**Escalate for deeper investigation if** a customer supplies evidence that unique records are missing despite acknowledged successful ingestion, there are relevant system errors, or a behavior deviates from documented semantics. An escalation package should include impact and timeline, version/service information, sanitized SQL, request/query IDs, session settings, row-count reconciliation, relevant system logs, and steps to reproduce. Never include secrets or raw personal information unnecessarily.

**Lab status:** Reproduction diagnosed and verified. **Fictional customer ticket remains pending confirmation**, not described as a closed production incident.
