# CH-001 — Successful INSERT Retry Without an Increase in Row Count

> **Simulation based on a documented ClickHouse behavior.** The customer ticket below is fictional. The SQL execution and recorded outcomes are from a real personal ClickHouse Cloud lab, not from a customer's production service.

## 1. Customer report (simulated)

> "Our application retries INSERT requests when a connection is interrupted. The retries are reported as successful, but the number of stored security-event records does not increase. Are we losing events?"

**Intake assessment:** Product reported as ClickHouse Cloud; ingestion/retry concern. Affected production service, timestamps, insert request IDs, impact, expected versus observed counts, and error responses are **not known** from an actual customer. Severity is therefore **not assigned**.

**Customer questions before accessing production:**
1. Which service, database and table are affected, and what access is authorized?
2. What were the exact client-side responses, timestamps, request/query IDs, and retry behavior?
3. How many **unique** events should have been stored? Are repeated requests identical or intentionally new?
4. Is ingestion entirely blocked, or are only repeated requests in question? Is an active security investigation affected?
5. Can the customer provide redacted INSERT statements, settings and diagnostic output without sharing sensitive events?

For this lab, access was limited to my own simulated environment.

## 2. Environment discovery (observed)

The investigation began with read-only discovery, rather than assuming the schema because I had created the environment.

```sql
SHOW DATABASES;
SHOW TABLES FROM support_lab;
DESCRIBE TABLE support_lab.windows_security_events;
SHOW CREATE TABLE support_lab.windows_security_events;
```

**Observed:** Five database names were visible, including `support_lab`. Its initial events table was `windows_security_events`, with six synthetic rows. The discovered schema contained `event_time`, `hostname`, `event_id`, `username`, `source_ip` and `description`.

The SQL Console truncated the displayed `SHOW CREATE TABLE` statement. I therefore queried table metadata rather than relying on a visually truncated result:

```sql
SELECT name, engine, sorting_key, partition_key
FROM system.tables
WHERE database = 'support_lab'
  AND name = 'windows_security_events';
```

**Observed for `windows_security_events`:** Engine `SharedMergeTree`; sorting key `event_time, hostname, event_id` (confirmed in a later, wider console view); empty partition key (no explicit partitioning). **This observation is for the original table, not proof of the engine used by `insert_retry_test`.** The test table's physical engine should be checked separately before asserting it.

Initial row-count baseline:

```sql
SELECT count() AS current_rows
FROM support_lab.windows_security_events;
```

**Observed:** `6` rows. This is **not** evidence that six is the correct number expected by a real customer.

## 3. Hypothesis and settings (observed)

A successful retry that does not produce additional rows could be explained by insert deduplication. Other possibilities include unsuccessful upstream delivery, asynchronous buffering, query filters, unexpected batching or deduplication-token reuse, and retry logic. None was assumed as the cause without a test.

The following read-only query inspected settings **for the current SQL session**, not guaranteed settings for any customer's application:

```sql
SELECT name, value, changed
FROM system.settings
WHERE name IN (
    'async_insert',
    'wait_for_async_insert',
    'insert_deduplicate',
    'async_insert_deduplicate'
)
ORDER BY name;
```

| Session setting | Observed value | `changed` |
| --- | --- | --- |
| `async_insert` | `1` | `1` |
| `wait_for_async_insert` | `1` | `1` |
| `insert_deduplicate` | `1` | `0` |
| `async_insert_deduplicate` | `1` | `1` |

The `changed` flag indicates whether a setting differs from its built-in default **in this SQL session**. The `insert_deduplicate` setting had `changed = 0`, while the other three had `changed = 1`. A value differing from its default does **not** mean the investigator personally modified it; the service or user profile may have supplied it. These results do **not** prove what settings a separate customer application used, nor by themselves prove that the particular INSERT statements went through an asynchronous buffer. `system.asynchronous_insert_log` would be an additional source of evidence; it was **not examined** in this case.

## 4. Controlled reproduction (observed)

A **separate test table** was created, so the original six synthetic security events were not changed:

```sql
CREATE TABLE support_lab.insert_retry_test
(
    batch_id String,
    event_id UInt32,
    message String
)
ENGINE = MergeTree()
ORDER BY (batch_id, event_id);
```

The starting count was verified using:

```sql
SELECT count() AS initial_rows FROM support_lab.insert_retry_test;
```

**Observed baseline:** `0`.

**First insert (executed once):**

```sql
INSERT INTO support_lab.insert_retry_test
(batch_id, event_id, message)
VALUES
('CH001-BATCH01', 4625, 'Failed login attempt'),
('CH001-BATCH01', 4720, 'User account created');
```

**Observed:** INSERT succeeded. A subsequent `SELECT * FROM support_lab.insert_retry_test;` returned the two records.

**Identical retry:** The same INSERT statement and values were executed again, once, without intentionally changing settings. This recreated an identical request from the SQL Console; it **did not** simulate a connection failure or verify the customer's actual retry client.

**Observed:** The retry returned `INSERT succeeded`, while:

```sql
SELECT count() AS total_rows
FROM support_lab.insert_retry_test;
```

still returned **`2`**, not `4`.

**Diagnostic corroboration:**

```sql
SELECT
    event_time,
    event_type,
    error,
    errorCodeToName(error) AS error_name
FROM system.part_log
WHERE database = 'support_lab'
  AND table = 'insert_retry_test'
ORDER BY event_time DESC
LIMIT 10;
```

**Observed:** The first write produced a normal operation with error code `0`; the retry produced error code **`389` — `INSERT_WAS_DEDUPLICATED`**. The screenshot visibly shows error code `389`; the long name is truncated by the console's available display width. This was the decisive evidence connecting the unchanged row count to deduplication **in the reproduction**.

**Additional diagnostic query for a future review (not run in the recorded session):**

```sql
SELECT
    event_time, query_id, event_type,
    part_name, rows, error,
    errorCodeToName(error) AS error_name
FROM system.part_log
WHERE database = 'support_lab'
  AND table = 'insert_retry_test'
ORDER BY event_time DESC
LIMIT 20;
```

`query_id` can support correlation with the relevant write or flush, but especially with asynchronous inserts, **do not assume it always equals the originating client request ID**; compare with `system.asynchronous_insert_log` and query logs when available. The outputs of this extended query have **not yet been captured**.

**Distinct new insert:**

```sql
INSERT INTO support_lab.insert_retry_test
(batch_id, event_id, message)
VALUES
('CH001-BATCH02', 4625, 'New failed login event');
```

After querying the records, **three total rows** were present: two from `CH001-BATCH01` and one from `CH001-BATCH02`.

Note: `batch_id` here is an application-defined field for readability, **not** automatically ClickHouse's deduplication identifier.

## 5. Findings and technical interpretation

| Check | Observed result |
| --- | --- |
| Test table initially | 0 rows |
| First INSERT | 2 rows persisted |
| Identical successful retry | Still 2 rows |
| `system.part_log` | `INSERT_WAS_DEDUPLICATED` (389) |
| Different subsequent INSERT | 3 total rows |

**Conclusion for this lab:** The same batch was recognized as a duplicate and skipped on retry, while different new data was still accepted. This is consistent with intended insert deduplication semantics; it is **not evidence of data loss** in the experiment.

**Limitations:** This was a small ClickHouse Cloud simulation, not a production-scale test. It did not reproduce a network failure, confirm the asynchronous buffer path from `system.asynchronous_insert_log`, test client retry SDKs, explicitly supplied `insert_deduplication_token` values, deduplication-window expiry, multi-replica behavior, or a real customer's configuration. It cannot establish whether a customer's allegedly missing *unique* events were ingested. On multi-replica ClickHouse Cloud deployments, many `system.*_log` queries are **replica-local**; use `clusterAllReplicas('default', system.part_log)` (subject to the service's cluster configuration and permissions) to examine all relevant replicas. Our displayed query inspected only the responding replica. See ClickHouse's [system-table debugging](https://clickhouse.com/blog/clickhouse-debugging-issues-with-system-tables) and [insert monitoring](https://clickhouse.com/blog/monitoring-troubleshooting-insert-queries-clickhouse) guidance.

## 6. Customer update (proposed wording; not sent)

> We reproduced the symptom in an isolated ClickHouse Cloud test. Repeating an identical successful INSERT did not increase the row count. The internal part log recorded `INSERT_WAS_DEDUPLICATED` (389), and a genuinely different INSERT was persisted normally. This indicates expected deduplication behavior in our test, not a confirmed production data-loss incident. To determine whether the same mechanism explains your reported events, please provide redacted examples of affected requests, their timestamps/query IDs, expected unique event counts, and relevant ingestion diagnostics. We recommend retaining retry deduplication while we review how the application constructs and retries batches, whether it sets `insert_deduplication_token`, and whether the client's expected new events are actually unique in the source.

## 7. Escalation decision and closure criteria

**No engineering escalation warranted solely by the controlled reproduction:** behavior was consistent with the documented mechanism.

**Escalate for deeper investigation if** a customer supplies evidence that unique records are missing despite acknowledged successful ingestion, there are relevant system errors, or behavior deviates from documented semantics. To reconcile expected and observed counts, compare **distinct stable source event identifiers** (not merely Windows `event_id`, which is an event *type*) against ingested identifiers for a defined time window, accounting for ingestion delay, filters, retries, and possible intentional deduplication. Our small test schema has **no unique per-event identifier**, so this reconciliation was **not performed**. An escalation package should include impact and timeline, version/service information, sanitized SQL, request/query IDs, session settings, row-count reconciliation, relevant system logs, and steps to reproduce. Never include secrets or raw personal information unnecessarily.

**Lab status:** Reproduction diagnosed and verified. **Fictional customer ticket remains pending confirmation**, not described as a closed production incident.

## 9. Reproducibility and cleanup (instructions, not an executed result)

For a fresh run, use a **new disposable table** or remove an existing disposable test table only after preserving all necessary evidence. Do **not** drop the original `windows_security_events` table. A rerunnable creation statement can use `CREATE TABLE IF NOT EXISTS support_lab.insert_retry_test ...`, but this alone will not reset row counts if the table already contains data.

**Optional cleanup after evidence capture, only in the personal lab and with explicit authorization:**

```sql
DROP TABLE IF EXISTS support_lab.insert_retry_test;
```

This command has **not been executed** in the documented session. It is destructive and would erase the test data, so it is not an appropriate unapproved action on a customer's production table.

**Further validation not performed:** Inspect the test table's actual engine; query `system.asynchronous_insert_log` for original and retry requests; correlate IDs in `system.part_log` and `system.query_log`; inspect `insert_deduplication_token` usage and deduplication windows under the customer's actual settings; then reconcile stable source event IDs against stored events.
