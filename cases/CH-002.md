# CH-002 — Why `LIMIT 10` still read more than half a million rows

**Simulated support case | ClickHouse Cloud, Azure | November 10, 2026**

**Finding.** A query returning ten failed-login events scanned inefficiently because `event_id` was absent from the table's sorting key. In a separate test table ordered by `(event_id, event_time, hostname)`, ClickHouse selected **1 of 61 granules** instead of 61 of 61. The corresponding query read **16,960 rows instead of 581,920 — 97.1% fewer** — and returned the same ten records.

**Boundary.** The original query completed in **7 ms**, so this is a demonstrated improvement in *data-read efficiency*, **not** a confirmed production latency incident. The customer, ticket, and dialogue below are simulated. The SQL outputs and numerical findings come from my own ClickHouse Cloud session.

## 1. The request and first response

> **Simulated customer:** "Our dashboard fetches the earliest ten failed login records with `LIMIT 10`, but ClickHouse reads far more data. Is the limit being ignored?"

My first response would be to confirm the service and query ID, request the exact SQL and representative timestamps, check whether users actually see a slowdown or a resource/cost concern, and ask whether other time-based queries depend on the existing table layout. I would not change a production sorting key based on one query.

For the exercise I prepared **500,000 synthetic events** in my own service. There was no access to a customer service, and no incident severity or SLA was assigned.

## 2. Inspect before modifying anything

I verified the dataset, described the table, and inspected its engine and keys rather than relying on how I had set up the lab.

```sql
SELECT count() AS total_events
FROM support_lab.ch002_events;

DESCRIBE TABLE support_lab.ch002_events;

SELECT name, engine, sorting_key, primary_key, partition_key
FROM system.tables
WHERE database = 'support_lab' AND name = 'ch002_events';
```

**Observed:** 500,000 events. Columns: `event_time DateTime`, `hostname String`, `event_id UInt16`. ClickHouse Cloud reported `SharedMergeTree` with sorting key `(event_time, hostname)`. Of the 500,000 events, **17** had `event_id = 4625`.

Here is the customer query as tested:

```sql
SELECT event_time, hostname, event_id
FROM support_lab.ch002_events
WHERE event_id = 4625
ORDER BY event_time ASC
LIMIT 10;
```

It returned ten records in **7 ms**. But the console reported reading **581,920 rows** (approximately 3.50 MB). A count of rows processed by a query is **not a count of unique events**; in this observed run the reported read count exceeded the table's 500,000 logical records.

## 3. Find out what ClickHouse is doing

I checked the plan rather than inferring a root cause from execution time:

```sql
EXPLAIN indexes = 1
SELECT event_time, hostname, event_id
FROM support_lab.ch002_events
WHERE event_id = 4625
ORDER BY event_time ASC
LIMIT 10;
```

**EXPLAIN output:** `ReadFromMergeTree`; `PrimaryKey`; `Condition: true`; `Parts: 1/1`; **`Granules: 61/61`**.

That is the relevant diagnosis: the primary index could not rule out any granule based on `event_id` because the data was primarily ordered by `event_time`. `LIMIT 10` restricts the result set; it does not necessarily reduce how much work ClickHouse must perform to find those rows.

I then inspected completed query records in `system.query_log`. The matching baseline entry reported:

| Query-log field | Baseline |
| --- | ---: |
| `read_rows` | **581,920** |
| `read_bytes` | **3,498,552** |
| `query_duration_ms` | **7** |
| `memory_usage` | **13,946,595** |
| `result_rows` | **10** |

These metrics belong to a specific completed execution. I did not combine results from unrelated queries returned by the log search.

## 4. Test one alternative without touching the original

I made a second table with the **same data** and an alternative sorting key:

```sql
CREATE TABLE support_lab.ch002_events_optimized
ENGINE = MergeTree()
ORDER BY (event_id, event_time, hostname)
AS
SELECT event_time, hostname, event_id
FROM support_lab.ch002_events;
```

The create operation succeeded and read the 500,000 source rows. I checked counts in both tables before running the comparison:

| Data check | Original | Comparison table |
| --- | ---: | ---: |
| Total rows | 500,000 | 500,000 |
| `event_id = 4625` | 17 | 17 |

These aggregate counts are **not a full row-by-row integrity check**. The copied dataset was synthetic and small enough for this controlled exercise.

I then ran exactly the same filtering and ordering query against `ch002_events_optimized`. Its `EXPLAIN indexes = 1` plan showed:

- `PrimaryKey` condition on `event_id = 4625`
- `Parts: 1/1`
- **`Granules: 1/61`**
- `Search Algorithm: binary search`

The new order concentrated matching events into a small range, allowing the primary index to reject other granules.

## 5. Evidence: what improved and what did not yet prove improvement

| Measurement | Original | Comparison table |
| --- | ---: | ---: |
| Index granules selected | 61/61 | **1/61** |
| Query-log rows read | 581,920 | **16,960** |
| Query-log bytes read | 3,498,552 | **194,183** |
| Query-log memory usage | 13,946,595 | **6,983,493** |
| Query-log duration | 7 ms | 4 ms |
| Result rows | 10 | 10 |

**Measured outcome:** 97.1% fewer reported rows read, about 94.4% fewer bytes read, and 60 of 61 granules excluded by the optimized primary-index condition.

**Do not overclaim:** 7 ms versus 4 ms came from single runs, without a repeated, controlled cache-aware benchmark. It cannot support a reliable latency-speedup percentage or a production SLA claim. The meaningful demonstrated improvement is resource efficiency for **this query pattern and synthetic dataset**.

I also compared the exact returned tuples from both queries, rather than assuming that matching counts implied matching answers:

```sql
WITH
(
    SELECT groupArray((event_time, hostname, event_id))
    FROM
    (
        SELECT event_time, hostname, event_id
        FROM support_lab.ch002_events
        WHERE event_id = 4625
        ORDER BY event_time ASC
        LIMIT 10
    )
) AS original_results,
(
    SELECT groupArray((event_time, hostname, event_id))
    FROM
    (
        SELECT event_time, hostname, event_id
        FROM support_lab.ch002_events_optimized
        WHERE event_id = 4625
        ORDER BY event_time ASC
        LIMIT 10
    )
) AS optimized_results
SELECT
    length(original_results) AS original_rows,
    length(optimized_results) AS optimized_rows,
    arraySort(original_results) = arraySort(optimized_results) AS results_match;
```

**Observed:** `original_rows = 10`, `optimized_rows = 10`, **`results_match = 1`**. This verifies the result *multiset* for this test, not the full table contents. Ordering would also need a deterministic tie-breaker for workloads with duplicate timestamps.

## 6. What I would tell the customer

> I reproduced the query shape using a separate ClickHouse Cloud test table. `LIMIT 10` correctly restricted the returned records; it did not prevent ClickHouse from reading a much larger range of data.
>
> The original table was ordered by timestamp, while the query filtered by event type. Its execution plan selected all 61 index granules. With an alternative ordering led by event type, only one granule was selected and the query read 97.1% fewer rows. I verified the ten returned records matched.
>
> This is a promising option for reducing resource usage, not an instruction to modify your production table immediately. Before choosing a production design, I'd review your other query patterns, ingestion volume, storage and migration cost, and whether a projection or alternate access path would be safer.

**Escalation/closure:** The lab finding is explained and reproducible. It is **not** a real customer ticket and was not closed with a customer. In production I would escalate if material latency or errors persisted after the access-plan diagnosis, or if a proposed design change affected service reliability. I would attach the affected query IDs, before/after plans, measured resource usage, representative workload queries, and rollback approach.

## 7. What this case does not establish

- No real customer system, issue, network interruption, outage, SLA or production performance regression was involved.
- The synthetic distribution is intentionally simple: 500,000 generated records, 17 failed-login events. It isn't a representative enterprise telemetry distribution.
- A sorting key that helps `event_id` filters might penalize time-only searches or ingestion/compression characteristics. **Choosing a production sort key requires workload-level analysis**, not one example query.
- I did not run repeated benchmarks with a controlled cache state, evaluate concurrency, or test projections, skipping indexes, streaming ingestion, migration or rollback.
- The comparison table existed solely for a non-destructive test. No production table was altered.
- ClickHouse Cloud system logs can be scoped to a responding replica; investigating an actual multi-replica service may require querying logs across replicas.
