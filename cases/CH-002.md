# CH-002 — Why a query returning ten events read much more data

**Simulated support case | ClickHouse Cloud, Azure | November 10, 2026**

**What I found.** The query returned ten failed-login events but read much more data to find them. The table was sorted by time, while the query filtered on event type. I tested the same records in a separate table sorted by event type first. ClickHouse then selected **1 of 61 data groups (granules)** rather than all 61, read **97.1% fewer rows**, and returned the same ten records. [Original query](../evidence/ch002/02-original-query-read.jpg) · [Optimized query](../evidence/ch002/08-optimized-query-read.jpg)

**Scope.** The original query took **7 ms**, which was already fast. This case shows less data being read, not a proven fix for a slow production service. The ticket is fictional; the SQL runs and screenshots are from my personal ClickHouse Cloud environment.

## 1. The request and first response

> **Simulated customer:** "Our dashboard fetches the earliest ten failed login records with `LIMIT 10`, but ClickHouse reads far more data. Is the limit being ignored?"

I'd ask for the affected service, the exact query and its query ID. I'd also clarify whether the customer is seeing delays or is concerned about how much data is read. Finally, I'd ask which other queries depend on the table. I would not change its sorting key without checking those workloads.

For the exercise I prepared **500,000 synthetic events** in my own service. There was no access to a customer service, and no incident severity or SLA was assigned.

## 2. Inspect before modifying anything

I first checked how many records were stored, which columns existed, and how ClickHouse had organized the table. I used discovery queries rather than assuming I knew the structure.

```sql
SELECT count() AS total_events
FROM support_lab.ch002_events;

DESCRIBE TABLE support_lab.ch002_events;

SELECT name, engine, sorting_key, primary_key, partition_key
FROM system.tables
WHERE database = 'support_lab' AND name = 'ch002_events';
```

**Observed:** 500,000 events. Columns: `event_time DateTime`, `hostname String`, `event_id UInt16`. ClickHouse Cloud reported `SharedMergeTree` with sorting key `(event_time, hostname)`. Of the 500,000 events, **17** had `event_id = 4625`.

Here is the customer query as tested:

```sql
SELECT event_time, hostname, event_id
FROM support_lab.ch002_events
WHERE event_id = 4625
ORDER BY event_time ASC
LIMIT 10;
```

It returned ten records in **7 ms**. But the console reported reading **581,920 rows** (approximately 3.50 MB). A count of rows processed by a query is **not a count of unique events**; in this observed run the reported read count exceeded the table's 500,000 logical records.

## 3. Find out what ClickHouse is doing

I checked the plan rather than inferring a root cause from execution time:

```sql
EXPLAIN indexes = 1
SELECT event_time, hostname, event_id
FROM support_lab.ch002_events
WHERE event_id = 4625
ORDER BY event_time ASC
LIMIT 10;
```

**EXPLAIN output:** `ReadFromMergeTree`; `PrimaryKey`; `Condition: true`; `Parts: 1/1`; **`Granules: 61/61`**.

**Why it happened:** ClickHouse had sorted the records by time. Its primary index therefore could not skip any of the 61 data groups when filtering by `event_id`. `LIMIT 10` limits the *answer*, not necessarily the amount of data searched. [See the original execution plan](../evidence/ch002/03-original-explain-61-61.jpg).

I checked `system.query_log` to confirm the work recorded for the original query. [View the query-log screenshot](../evidence/ch002/04-baseline-query-log.jpg).

| Query-log field | Baseline |
| --- | ---: |
| `read_rows` | **581,920** |
| `read_bytes` | **3,498,552** |
| `query_duration_ms` | **7** |
| `memory_usage` | **13,946,595** |
| `result_rows` | **10** |

These figures come from one identified query execution, rather than a mixture of different queries.

## 4. Test one alternative without touching the original

I created a **separate test table**, leaving the source table untouched, and copied the existing records with a different sort order:

```sql
CREATE TABLE support_lab.ch002_events_optimized
ENGINE = MergeTree()
ORDER BY (event_id, event_time, hostname)
AS
SELECT event_time, hostname, event_id
FROM support_lab.ch002_events;
```

The create operation succeeded and read the 500,000 source rows. I checked counts in both tables before running the comparison:

| Data check | Original | Comparison table |
| --- | ---: | ---: |
| Total rows | 500,000 | 500,000 |
| `event_id = 4625` | 17 | 17 |

These checks confirm the totals, not full row-by-row equality. [View the count comparison](../evidence/ch002/06-data-counts-match.jpg).

I then ran exactly the same filtering and ordering query against `ch002_events_optimized`. Its `EXPLAIN indexes = 1` plan showed:

- `PrimaryKey` condition on `event_id = 4625`
- `Parts: 1/1`
- **`Granules: 1/61`**
- `Search Algorithm: binary search`

With matching event types stored together, ClickHouse could skip most of the data groups. [See the optimized plan](../evidence/ch002/07-optimized-explain-1-61.jpg).

## 5. Before and after

| Measurement | Original | Comparison table |
| --- | ---: | ---: |
| Index granules selected | 61/61 | **1/61** |
| Query-log rows read | 581,920 | **16,960** |
| Query-log bytes read | 3,498,552 | **194,183** |
| Query-log memory usage | 13,946,595 | **6,983,493** |
| Query-log duration | 7 ms | 4 ms |
| Result rows | 10 | 10 |

**Measured result:** The comparison query read **97.1% fewer rows** and about **94.4% fewer bytes**. ClickHouse skipped 60 of the 61 data groups. The query logs show these figures for the [original](../evidence/ch002/04-baseline-query-log.jpg) and [comparison](../evidence/ch002/09-optimized-query-log.jpg) executions.

**What I can't claim:** The 7 ms and 4 ms readings are single runs. I did not repeat the test under controlled cache conditions or realistic traffic. So I am not claiming a reliable speed improvement for a production service.

I also compared the exact returned tuples from both queries, rather than assuming that matching counts implied matching answers:

```sql
WITH
(
    SELECT groupArray((event_time, hostname, event_id))
    FROM
    (
        SELECT event_time, hostname, event_id
        FROM support_lab.ch002_events
        WHERE event_id = 4625
        ORDER BY event_time ASC
        LIMIT 10
    )
) AS original_results,
(
    SELECT groupArray((event_time, hostname, event_id))
    FROM
    (
        SELECT event_time, hostname, event_id
        FROM support_lab.ch002_events_optimized
        WHERE event_id = 4625
        ORDER BY event_time ASC
        LIMIT 10
    )
) AS optimized_results
SELECT
    length(original_results) AS original_rows,
    length(optimized_results) AS optimized_rows,
    arraySort(original_results) = arraySort(optimized_results) AS results_match;
```

**Observed:** `original_rows = 10`, `optimized_rows = 10`, **`results_match = 1`**. The same ten result tuples were returned in this test. This does not prove that every row in both tables is identical. A real query could also need an additional sort field if several events share the same timestamp. [View the matching-results screenshot](../evidence/ch002/10-results-match.jpg).

## 6. Proposed customer response (not sent)

> I reproduced the query shape using a separate ClickHouse Cloud test table. `LIMIT 10` correctly restricted the returned records; it did not prevent ClickHouse from reading a much larger range of data.
>
> The original table was ordered by timestamp, while the query filtered by event type. Its execution plan selected all 61 index granules. With an alternative ordering led by event type, only one granule was selected and the query read 97.1% fewer rows. I verified the ten returned records matched.
>
> The separate test suggests an option for reducing the data read by this query. I would not recommend changing your production table yet. I'd first review other important queries, incoming data volume, and the cost and risk of rebuilding the table. We could also assess a projection, which may provide a second access pattern without replacing the original table's sorting order.

**Next steps if this were a real ticket:** I'd share the findings, ask whether reducing resource usage addresses the customer's concern, and check other important query patterns before recommending a change. I would escalate unresolved slowness, errors, or migration risks with the query IDs, screenshots, measured resource usage, and a proposed rollback plan. **No real ticket was resolved or closed.**

## 7. What this case does not establish

- No real customer system, issue, network interruption, outage, SLA or production performance regression was involved.
- The synthetic distribution is intentionally simple: 500,000 generated records, 17 failed-login events. It isn't a representative enterprise telemetry distribution.
- A sorting key that helps `event_id` filters might penalize time-only searches or ingestion/compression characteristics. **Choosing a production sort key requires workload-level analysis**, not one example query.
- I did not run repeated benchmarks with a controlled cache state, evaluate concurrency, or test projections, skipping indexes, streaming ingestion, migration or rollback.
- The comparison table existed solely for a non-destructive test. No production table was altered.
- ClickHouse Cloud system logs can be scoped to a responding replica; investigating an actual multi-replica service may require querying logs across replicas.
